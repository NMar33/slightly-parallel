name: daily-standup
description: "Write the project's standup for yesterday from every chat of that day, with a helper agent on a smaller model. Use when the [slightly-parallel] notice says there is no standup for a day, or when the operator types #standup."
---

One standup per project per day. It covers every chat of that day and is
written the next time anyone works on the project. You do not write it
from memory: a helper agent reads the day's messages.

1. The `[slightly-parallel] No standup for <date> …` notice gives the date, how many
   messages there were, and the model. If the notice says to ask, ask the
   operator before other work, in one short message: "Yesterday (<date>)
   has no standup: <N> messages in <M> chats. Write it now with a helper
   agent on <model>, or postpone?"
   - Write it now: go to step 2.
   - Postpone, or later: call `standup_postpone {date, hours}` (4 hours
     when the operator names no time). Nobody is asked again until then.
   - Another model: use the one the operator names.
2. Start a helper agent on that model (in Claude Code: the Agent tool with
   `model`). Give it this whole prompt and nothing else:

   > Write the Slightly Parallel standup for <date>. Call the MCP tool
   > `standup_material {date: "<date>", claim: true}`. If the answer says
   > the standup is written, or another agent has claimed it, stop and say
   > so. Otherwise follow the `instructions` in the answer exactly, using
   > only the `chats` in the answer as your material. Then call
   > `write_entry {lens: "standup", fields: {summary, deviation, movement,
   > detail, for_date: "<date>"}}`. Reply with the summary line only.

   If your tool has no helper agents, do the same steps yourself.
3. When the helper is done, tell the operator the summary line in one
   sentence, and go on with their request.

The instructions for the text come with the material, from the server, so
they are the operator's current ones. Do not paraphrase them to the helper.

Check: open Standups in Slightly Parallel. The day shows one standup. A refusal from
`write_entry` names what is wrong: fix it and write again.

Mistakes to avoid: writing the standup yourself from what you remember of
one chat; asking again after the operator said later; starting a second
helper when the answer says another agent has claimed the day.

**Standup — one per project per day.** It covers every chat of one day
and is written the next time anyone works on the project. The
`[slightly-parallel] No standup for …` notice tells the first agent of the day; the
skill `daily-standup` has the steps: ask the operator (write it now, or
postpone — `standup_postpone {date, hours}`, 4 hours by default, and
nobody is asked about that day again until then), then a helper agent on
the model the notice names reads the
day with `standup_material {claim: true}` and writes it with
`write_entry {lens: "standup"}`. `#standup` asks for it by hand.

The team lead reads it the next morning. Write it as section 3 says. 250
words at most for the whole standup. Read the last messages of the day
first: what the operator already decided is reported as decided, not as
an open question.

- `summary` — one sentence, 25 words at most: the one or two changes that
  matter most, as facts about the product.
- `deviation` — at most 3 items, one sentence each: something a user
  would have seen broken, work that was redone, or a correction from the
  operator — with the cause and the state now. Nothing of the kind: leave
  it empty.
- `movement` — at most 6 items, the most important first, 35 words at
  most each. One item is one outcome a user or an agent can see: what
  they can do now that they could not before. Write a state only when
  the item is not finished: what is left, and who it waits on. Give a
  task as its title, then its id, and only on its own work. `deviation`
  says what went wrong; `movement` says how things stand now: no fact in
  both. Put small fixes together in one last item.
- `detail` — three short parts, each may be empty. **Needs an answer:**
  each question or offer left with the operator that is still open, with
  only the options that were given. **Next:** what the last messages say
  happens next. **State:** one line — were the tests run, is the work
  pushed, what is started and not finished, and what the operator must do
  in a running session (reconnect, reload).
- `for_date` — the day it covers, `YYMM-DD`.

Leave out: how the work was done (helper agents, tools, test counts,
commits), and what the operator said themselves.

  "movement":[
    "Evidence upgrade (tk_0e571cfa): typing #evidence now sends the agent the operator's own saved prompt, the same as a done-report does.",
